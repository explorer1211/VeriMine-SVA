# N0 工程预处理

输入：一份 `status: confirmed`、`unresolved` 为空的 YAML 配置（可通过 `design.filelist` 引用 .f）。
输出：规范化配置、四层哈希、源文件快照，以及 design / revision / run 三条记录。

```bash
pip install -e '.[dev]'
verimine n0 examples/fifo/verimine.yaml            # 校验、哈希、快照、落库
verimine n0 examples/fifo/verimine.yaml --dry-run  # 只校验和计算哈希
verimine n0 examples/fifo/verimine.yaml --json     # 完整结果
verimine schema --out schemas/verimine-config.schema.json
```

退出码：0 成功；1 校验失败（所有错误一次列出）；2 配置未确认（status 不是 confirmed 或 unresolved 不为空）。

## 步骤与代码位置

| 步骤 | 内容 | 代码 |
|---|---|---|
| 0 | 入口检查：在 schema 校验之前，只看 status 和 unresolved | `n0/load.py: entry_check` |
| 1 | 读取 YAML，展开 .f（-f/-F 嵌套、+incdir+、+define+、-v、-y、+libext+、环境变量），与 YAML 合并 | `n0/filelist.py`、`n0/load.py` |
| 2 | 校验：pydantic 模型（JSON Schema 由它导出）+ 文件存在/可读、不跑出 root、top 已填、时钟复位合法、文件不重复 | `config.py`、`n0/load.py` |
| 3 | 规范化配置对象 | `n0/load.py` |
| 4 | slang 预处理，收集所有被 `include 的文件（含嵌套） | `n0/includes.py` |
| 5 | 四层哈希 | `n0/pipeline.py: compute_hashes` |
| 6 | 记录工具版本 | `n0/tools.py` |
| 7 | 按内容哈希快照 | `n0/store.py: snapshot` |
| 8 | 写入 design / revision / run（SQLite） | `n0/store.py: record` |

默认工作区是 `<root>/.verimine/`：`store/objects/` 是快照，`verimine.db` 是数据库，`runs/<run_hash>/n0.json` 是本次结果。

## 四层哈希

所有哈希都是 `sha256("verimine/<层名>/v1\0" + 规范 JSON)`，路径一律相对 root，所以整个工程搬目录哈希不变。

| 层 | 内容 |
|---|---|
| source_hash | 所有源文件、库文件、头文件的 (相对路径, 内容哈希)，按路径排序。内容哈希先把 CRLF 统一为 LF |
| build_hash | source_hash + top、编译顺序、include 路径、宏、参数覆盖、语言标准、黑盒、库文件/库目录/libext、assumes |
| env_hash | 时钟复位定义 + 工具版本；若配置了 `env.docker_digest` 则用镜像 digest 代替工具版本 |
| run_hash | build_hash + env_hash + LLM 提供方/模型/提示词集版本 + 随机种子 + profile + 算法参数 |

不参与哈希：`status`、`unresolved`、`design.name`（只是显示名）、`waveforms`（见下方“待定”）。

## 实现时做的取舍（规格里没写死的地方）

- **.f 相对路径**：按 Verilator 约定。`-f` 引入的文件里，相对路径相对 root；`-F` 引入的文件里，相对路径相对该 .f 所在目录。YAML 里 `design.filelist` 的条目按 `-f` 处理。很多项目的 .f 是相对自身目录写的（如 Ibex 的 `rtl/ibex_core.f`），此时用一个包装 .f 写 `-F rtl/ibex_core.f`，或把 root 设为 .f 所在目录。
- **合并顺序**：文件、include 路径都是 .f 的条目在前、YAML 的在后。同名宏 YAML 覆盖 .f，值不同时给警告 `N0_DEFINE_OVERRIDE`。宏值统一转字符串，`WIDTH: 8` 与 `WIDTH: "8"` 哈希相同。
- **同一文件重复**：按 inode 判断，`rtl/a.sv` 和 `rtl/./a.sv`、符号链接都算重复。
- **不跑出 root**：先解析符号链接再判断，指向 root 外的链接也会被拒绝。被 include 的头文件在 root 外同样报错，因为快照和相对路径哈希都要求文件在 root 内。
- **include 收集**：所有编译单元放进一次 slang 预处理（宏跨文件可见，与仿真器一条命令编译的行为一致）。只收集当前宏取值下生效的 `ifdef 分支里的 include；宏取值本身在 build_hash 里，所以这是精确的。找不到 include 是错误（否则哈希不完整）；其他语法诊断只作为警告，交给 N1。
- **-y 库目录**：N0 不做 elaboration，无法知道库目录里哪些文件真正被用到，所以目录下所有匹配 libext 的文件都纳入 source_hash（保守：库目录里任何文件变化都会产生新 revision）。
- **LLM 关闭时**：`llm.mode: off` 时忽略 provider/model 等残留字段，避免同一次运行被当成不同 run。
- **快照内容**：存的是 CRLF→LF 后的内容，保证对象文件的 sha256 就是它的文件名，可以随时校验。
- **YAML 解析**：用 ruamel.yaml（YAML 1.2），`mode: off` 读成字符串 `"off"`；PyYAML（YAML 1.1）会读成 `False`。
- **落库幂等**：revision 主键是 build_hash，run 主键是 run_hash；同一输入重复运行不新增记录，只改种子只新增 run。
- **命令行**：用标准库 argparse，没有引入 typer/click。

## 待定

- `waveforms` 目前只校验存在且在 root 内，不参与任何哈希。波形会影响挖掘结果，建议在用到波形的阶段（N2 之后）把波形内容哈希并入 run_hash，需要确认放在哪一层。
- 多时钟只给警告 `N0_MULTICLOCK`，按规格由 N1 给出 `UNSUPPORTED_MULTICLOCK`。

## 实测

- `examples/fifo`：.f 嵌套 + include + package，通过。
- PicoRV32（单文件 `picorv32.v`）：通过。
- Ibex（`rtl/ibex_core.f`）：原 .f 不含 `prim_assert.sv`、`dv_fcov_macros.svh` 所在的 include 路径，N0 逐行报出 16 处 `N0_INCLUDE_MISSING`；补上两个 `+incdir+` 后通过，收集到 17 个源文件和 5 个头文件（含 `prim_assert_standard_macros.svh` 等嵌套头文件）。
