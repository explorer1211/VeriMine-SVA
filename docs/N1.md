# N1 结构索引

输入：N0 已确认的配置（`status: confirmed`、`unresolved` 为空）。
输出：完整实例树的结构索引、四层哈希之外的 `index_hash`、模块指纹、模块状态、时钟域分析，以及 slang/Verilator/Yosys 三工具基准检查结果。

```bash
verimine n1 examples/fifo/verimine.yaml            # elaboration + 基准检查 + 落库
verimine n1 examples/fifo/verimine.yaml --dry-run   # 只跑不写库
verimine n1 examples/fifo/verimine.yaml --json      # 完整 JSON 结果
```

退出码沿用 N0：0 成功；1 校验失败；2 配置未确认。

| 5 | 三工具基准检查（slang/Verilator/Yosys）+ 端口交叉比对 | `n1/baseline.py` |

## 结构索引包含什么

每条实例记录：

| 字段 | 内容 |
|---|---|
| `path` | 层级路径（如 `top.u_child`） |
| `module` | 所属模块定义名 |
| `parent` | 父实例路径 |
| `params` | 该实例的参数取值（已展开） |
| `ports` | 端口名、方向、类型、是否来自 interface |
| `signals` | 线网或变量、类型、声明位置 |
| `procs` | 过程块类型（always_ff/always_comb/always_latch/always/assign/initial）、敏感列表及边沿 |
| `drivers` | 每个信号由哪些过程块驱动 |
| `clk_rst_candidates` | 候选信号、极性、同步/异步、依据 |
| `clocks` | 该实例涉及的时钟集合（已排除配置中的复位） |
| `is_incomplete` | elaboration 是否有 error |

## 模块状态

| 状态 | 含义 | 后续处理 |
|---|---|---|
| OK | 三工具都通过，无严重告警 | 正常进入 N2 |
| OK_WITH_WARNINGS | 有锁存器、宽度告警等 | 进入 N2，告警写入索引，N8 可引用 |
| BLOCKED | 某工具处理不了，或多驱动/组合环 | 不进入后续流程，报告写明原因和位置 |
| CONTAINS_BLOCKED | 自身没问题但子模块被阻 | 提示把被阻塞子模块设为黑盒后继续 |

状态按实例树自底向上传播：子模块 BLOCKED 会让父模块变成 CONTAINS_BLOCKED，除非父模块自己也 BLOCKED。黑盒选择记录进配置，参与 `build_hash`（由 N0 处理）。

## 指纹

指纹 = `sha256("verimine/module_fp/v1\0" + JSON([tokens, sorted_params, sorted_child_fps]))`

- `tokens` 是预处理后的 token 流（不含注释和空白），所以宏定义变了指纹会变。
- `sorted_params` 是该实例的参数取值，所以同模块不同参数实例化指纹不同。
- `sorted_child_fps` 是子模块指纹，所以子模块变了父模块指纹也变。

验收：只改注释和空白，指纹不变；改一行逻辑，该模块和所有祖先的指纹都变（见 `test_comment_change_does_not_change_fingerprint`、`test_child_change_propagates_to_parent_fingerprint`）。

## 索引哈希

`index_hash = sha256("verimine/index/v1\0" + 规范 JSON)`

规范 JSON 里所有列表按固定顺序输出（按路径/名称排序），路径全部相对 root，不含绝对路径、时间戳、机器名。同一个 `build_hash` 重跑两次，`index_hash` 必须一致（见 `test_index_hash_deterministic`）。N2 以后的节点把它当作输入哈希。

## 时钟域分析

- 从每个实例 `always_ff`/`always` 块的敏感列表里收集带边沿的信号。
- 配置里的复位信号（`resets[].name`）从时钟集合里剔除，不计为时钟。
- 涉及多个时钟的实例标记 `N1_UNSUPPORTED_MULTICLOCK`，报告里写明模块名和时钟列表。
- 跨时钟域信号（同一信号被多个时钟域的过程块驱动）列入 `cdc_signals`，仅报告不验证（`N1_CDC_SIGNAL`）。

## 三工具基准检查

不加断言，分别让 slang、Verilator、Yosys 处理一遍设计：

| 工具 | 检查内容 |
|---|---|
| slang | elaboration 有无 error、未解析模块、端口宽度不匹配 |
| Verilator | `--lint-only -Wall`：锁存器、多驱动、组合环、宽度、不完整敏感列表、未驱动信号 |
| Yosys | `read_verilog -sv -formal` + `hierarchy -check` + `proc` + `check` |
| 交叉比对 | slang 与 Yosys 的顶层端口列表是否一致（`N1_PORT_MISMATCH`） |

Verilator 命令加了 `-Wno-DECLFILENAME` 以忽略文件名与模块名不匹配的告警（临时文件场景）。

Yosys 的 Verilog 前端对部分 SystemVerilog 构造（如 `import pkg::*`）支持有限，遇到时会报 BLOCKED——这是真实工具能力上限的体现，不是 N1 的 bug。后续可在 N0 把 package 内联展开，或改用 Yosys 的 `verific` 后端（需要 license）。

## 落库

SQLite 表（与 N0 的表同库，前缀 `n1_`）：

| 表 | 主键 | 内容 |
|---|---|---|
| `n1_index` | `build_hash` | schema 版本、index_hash、top_path、是否不完整 |
| `n1_instance` | `(build_hash, path)` | 模块名、父实例、参数、时钟集合 |
| `n1_port` | `(build_hash, inst_path, name)` | 方向、类型、是否 interface |
| `n1_signal` | `(build_hash, inst_path, name)` | 种类、类型、声明位置 |
| `n1_proc` | `(build_hash, inst_path, seq)` | 类型、敏感列表、位置 |
| `n1_driver` | `(build_hash, inst_path, seq)` | 信号、驱动种类、过程块类型、位置 |
| `n1_module_status` | `(build_hash, path)` | 状态、原因、阻塞工具、阻塞码 |
| `n1_fingerprint` | `(build_hash, inst_path)` | 指纹哈希 |

所有写都是 `INSERT OR IGNORE`，同一个 `build_hash` 重跑不新增记录。完整结果同时写到 `runs/<run_hash>/n1.json` 方便人工对比。

## 实现时的取舍

- **slang 同时做索引和基准检查**：elaboration 的诊断直接作为 slang 基准报告，不再单独跑一次。
- **驱动关系用 slang 的 `AnalysisManager`**：`getDrivers(symbol)` 返回每个信号的驱动列表，多个 Procedural 驱动即多驱动。
- **敏感列表从 `TimedStatement.timing` 提取**：`EventList.events` 里每个 `SignalEvent` 有 `edge` 和 `expr.symbol.name`。
- **指纹用独立 Compilation**：和 elaboration 分开跑，避免分析状态污染指纹。定义级 token 缓存（同模块多实例共享）。
- **Yosys 端口解析**：从 `select -list` 之前的 read 日志里解析 `module top (input ... output ...)` 段，做方向归一化（slang 的 `in`/`out` 对齐 Yosys 的 `input`/`output`）。
- **CDC 只做启发式报告**：同一信号在多个时钟域的过程块里被驱动就列为 CDC 候选，不做形式化验证。
- **不支持构造的识别**：扫描 slang 诊断里的 `real`、`#`（延时）、`force`/`release`、`$time`/`$realtime` 等关键字，标 `N1_UNSUPPORTED`。

## 待定

- Yosys 对 SystemVerilog package 的支持有限，fifo 示例因此被标 BLOCKED。后续考虑在 N0 阶段做 package 内联，或在 N1 检测到 package import 时改用 Yosys 的 `verific` 后端（需 license）。
- 组合环检测目前依赖 Verilator 的 `COMBDLY` 告警，slang 侧没有专门检测。
- 黑盒机制尚未接通：N1 报告 CONTAINS_BLOCKED 后，需要用户在 YAML 里把对应模块加入 `design.blackbox`，再重跑 N0+N1。这条链路要等 N0a 配合。
